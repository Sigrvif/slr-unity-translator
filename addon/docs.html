SLRUnity

The SLRUnity is an addon that adds a new game engine to SLR Translator, so Unity games (both IL2CPP and Mono scripting backends) can be translated the same way RPG Maker games are: with the DSLR translation engine, glossaries and SLR's QC pipeline. It ships its own Python backend and runtime, so nothing extra has to be installed. The game itself is never modified — and since the scan stages a copy of every string-bearing file inside the project, the project is self-contained: you can translate, save, reopen and export long after moving or deleting the original game folder (only the optional full game copy export still needs it).

This page is shipped by the addon (its docs field in package.json — see Shipping a documentation page). The same content also travels inside the addon as assets/help.html for SLR builds without the addon documentation system.

What this addon does

  • Find every user-visible translatable string in the game's data files: serialized scene/object fields (type-trees), raw length-prefixed text records, IL2CPP global-metadata.dat string literals, Mono DLL code literals, TextAsset payloads (JSON/CSV/...) and plain text files. Japanese strings are all collected; non-Japanese strings (official English UI like an Achievement button, the game's own english(en) localization tables, credits) are collected from display text only — TMP/Text fields, Localization tables, text components — so engine-internal names stay out. Everything is risk-tagged so only the safe tiers are translated by default (see String tags). Fonts and textures are catalogued too.
  • Stage the game into the project. At creation, every file the scan found strings in — and every file bearing an embedded font — is copied into the project's staging cache; the saved .slrproj carries them, so the project is self-contained and the original game folder is only needed again for a full game copy export.
  • Write translations back on export — by default as a small file-replacement patch you copy over the game folder, or as a full standalone copy of the game (folder or zip). No runtime hooks, no BepInEx, no patcher; the original game is never touched.
  • Swap the game's embedded fonts with SLR Translator's own condensed CJK font SLRCondensedCJK (already shipped by the app for SEP rendering; no font is bundled with the addon) so translated English renders narrow and untranslated Japanese still renders, and re-render the font atlases of TextMeshPro assets from SLR's fonts (Latin/UI text from Stint Ultra Condensed, Japanese from SLRCondensedCJK) — see Fonts.
  • Round-trip images through SEP (see SEP Picture Translation) for image-text translation — as two standalone tools on the New Project slide: extract game textures for SEP, then insert SEP's rendered images into a game copy. The image workflow is independent of any translation project.
  • Remove mosaic censorship without a project — a third standalone tool patches a game's mosaic layers directly and packs the changed files into a drop-in zip, so already-translated games can be treated without creating a translation project. See Demosaic.

Installing

Short version: extract the downloaded archive (SLRUnity-version-win.zip, e.g. SLRUnity-2.8.1-win.zip, or the smaller .7z) into www/addons/, then restart SLR Translator. To remove the addon, delete the SLRUnity folder. See also Installing an addon.
  1. Find the addons folder: open your SLR Translator installation folder (the one containing SLR Translator.exe) and inside it www/addons/ (create it if it does not exist).
  2. Extract the archive into it: right-click the downloaded SLRUnity-version-win.zip → Extract All (Windows opens .zip files by itself; a .7z needs 7-Zip or similar but is smaller), extracting INTO www/addons/. The package wraps everything in one SLRUnity/ folder, so the result is www/addons/SLRUnity/ directly containing package.json, UnityAddon.js, lib/, backend/, runtime/, docs.html and assets/. Do not extract into an extra nested folder of the same name.
  3. Restart SLR Translator. The New Project dialog now shows a SLRUnity entry (with its own icon) — pick it, press Select Folder and choose the game folder. Unity games are detected automatically; no engine has to be picked by hand.
Removing / updating: delete (or replace the contents of) www/addons/SLRUnity/ and restart. Nothing else is left behind except the addon's own entry in data/config.json, which is harmless. To update, extract the new archive over the old folder the same way.

The workflow

The SLRUnity slide in the New Project dialog offers four clearly separated actions. Strings and images are two independent workflows: the strings project never touches images, the image tools never need a project — and mosaic removal works with or without one.

  1. Strings: create a translation project. New Project → SLRUnity entry → Select Folder, then pick the game folder (or the game's .exe). The engine detects Unity via UnityPlayer.dll / GameAssembly.dll or a <Game>_Data folder with Unity data files. Progress streams into the project-creation console; a typical game takes a few minutes. After the scan the console shows Staging files i/n name lines while every string-bearing file is copied into the project (the self-contained copy), plus a Tags: line splitting the strings by risk. The result is a normal SLR project: one entry per file (scenes like level0 first, then metadata, TextAssets, text files), one row per string, with UI hierarchy contexts in Row Properties — and every row carries its risk tag (see String tags).
  2. Strings: translate. Everything standard SLR from here: extract/generate a glossary, DSLR batch translation (auto, or manual row editing), QC checks — see Your First Translation Project. Leave rows blank to skip them — blank translations are never written into the game. Rows tagged yellow/red (and their no-Japanese variants) are skipped by batch translation until you promote them.
  3. Strings: export. Export with mode Folder or Zip, and pick the Export kind — patch (changed/selected files only) (default) or full game copy — plus the optional Replace game fonts (see Export options). The default patch export produces a small folder of replacement files to copy over the game; the summary reports strings written, files exported, fonts swapped and TMP font atlases re-rendered.

String tags — what gets translated by default

The scan collects everything user-visible, then tags every row by how safe it is to translate, using SLR's own per-row tags — so SLR's batch translation applies its default blacklist automatically: rows tagged yellow, red, gray, gold or darkred are skipped; untagged and green rows are translated. A risky row is never lost — it sits in the project until you decide.

TagMeaning
(no tag)Display text — always safe. Translated by default. UI labels (m_Text), line-based dialogue scripts.
greenScript text confirmed safe. Translated by default. Code literals (global-metadata.dat, Mono DLLs — the intro cinematics many games keep in code), patched by purpose-built writers.
yellowLikely safe, confirm first (not translated by default). Japanese in non-display fields, JSON/CSV values — game data (name/stat tables) in some titles.
redLikely structural — leave alone unless you know the game (not translated by default). Object/asset names, keys, cue/event names, data-table rows, asset filenames.
gray / gold / darkredThe no-Japanese variants, applied when the Japanese source general option is on: gray = untagged but without Japanese (official English UI), gold = yellow without Japanese, darkred = red or green without Japanese.

To translate a yellow/red row, retag it (right-click → Tags) or uncheck those colors in the batch dialog's blacklist — once you choose to translate a tagged row it is patched like any other. The export always writes every non-blank translation regardless of tags; tags only decide what batch translation picks up by default.

The image round-trip is separate and does not require (or create) a translation project:

  1. Extract textures. On the same SLRUnity slide, press Select Game Folder & Extract Textures and pick the game. Every Texture2D is dumped as a PNG into <Game>_unity_img next to the game, together with a manifest (unity_img_manifest.json). Progress runs in the loading console; the game itself is never modified.
  2. Prune + SEP. Delete the images you do not want translated, then create an SEP project on that folder (New Project → SEP).
  3. Translate + render. In SEP, OCR → translate → render the images, then export SEP's rendered images to a folder (e.g. <Game>_unity_img_translated).
  4. Insert. Back on the SLRUnity slide, use Insert translated images into a game copy: pick the game folder, the extracted-images folder (the one with unity_img_manifest.json), SEP's rendered-images folder and an output folder — optionally tick Replace game fonts. The tool copies the game and applies the rendered images (a summary reports textures imported and fonts swapped). To translate strings and images, export the strings project first and run Insert on that exported copy (or vice versa — the tools are independent).

The mosaic quick-fix is the fourth action on the slide, Select Game Folder & Remove Mosaic: it runs the demosaic treatment (below) on any game directory without creating a translation project — the quick way to treat a game that is already fully translated. Pick the options (detection level, Reveal instead of hide, Patch code-level censorship — your selection is remembered), pick the game folder, and the tool packs only the changed files into <Game>_demosaic.zip next to the game: extract its contents over the game folder to apply; remove the files it contains to undo. A run that finds nothing says so (try the medium detection level).

Export options

Export from a Unity strings project writes the translations (and optionally the font swap) — image re-import is not part of it; use the standalone Insert translated images tool described above. The export runs under the same loading overlay/console as project creation: a Processing preamble, one console line per patched file (Unity export), one line per reverted original (Including original i/N), a Packing archive… line in zip mode, and the summary as console lines (Export complete, mode, counts, output). The overlay stays up with the finished log until you close it — there is no extra popup on success; only failures alert, after the overlay has ended.

OptionEffect
Export kind: patch (changed/selected files only) (default) Exports the files actually changed this run, as whole-file replacements at their game-relative paths — read from the copy staged inside the project, so it works even if the original game folder is gone. Apply it by copying the exported files over your game folder (a copy of the game, or a previous export). Small and fast; the summary reports files exported.

Everything else comes out as originals (revert): every file in scope that the patch did not change is exported as its original (staged) bytes, so the patch always covers its full scope — copy it over a previous export to revert. With no file selection the scope is all project files (export everything); with files checked in the project's file list, only those files are in scope. Exporting with no translations at all is therefore valid: it produces an all-originals baseline patch.
Export kind: full game copy The classic whole-game export: a complete standalone copy of the game (patched in place), as a folder or a zip. Needs the original game folder to still exist where the project was created — if it is gone, the export tells you to use patch export instead (the project is self-contained) and does nothing.
Replace game fonts Two things: (1) swaps the game's embedded Japanese fonts with the dialogue font, and (2) re-renders the baked glyph atlases of TextMeshPro font assets — the JP dialogue font from the dialogue face, every other (Latin/UI) TMP font from the UI face — so narrow English shows up even in games whose TMP atlases are frozen. The two faces are SLR Translator's own — a Japanese-capable condensed face for dialogue (SLRCondensedCJK, because untranslated Japanese must keep rendering) and a narrower Latin-only face for UI (Stint Ultra Condensed, because pure UI text never needs Japanese glyphs and the narrow face fits translated English best) — unless you supply your own: the two Custom font fields below the checkbox take absolute paths to your own .ttf/.otf (with a Browse… button each); your choices are remembered for the next export. If a resolved font file is missing, the export logs a WARNING line in the overlay console and skips only the affected stage (strings are still patched). In patch mode the swap/bake adds only the font-bearing files to the patch. See Fonts.
Remove mosaic censorship (demosaic) Off by default — opt in per export. Detects the game's mosaic-censorship layers in its own data files and patches them out of the export: dedicated mosaic objects are hidden, mosaic materials are neutralized by swapping their shader for the game's own transparent one. Your original game is never modified, and exporting again with the box unchecked reverts everything. See Demosaic.
Demosaic detection level High confidence only (recommended) patches only unambiguous candidates — mosaic-named objects/materials/shaders, or shaders with explicit mosaic properties. Include medium confidence also patches weaker matches (e.g. a shader that only carries the typical mosaic size parameters): more coverage on stubborn games, higher false-positive risk.
Reveal instead of hide (advanced) For mosaic materials sitting on modeled body meshes: instead of making them invisible, their shader is swapped for the game's own display shader (its body/skin shader, found automatically) and the textures are kept — so a mesh whose censorship was done by shader shows its real texture. The option to try when the standard removal makes body parts disappear entirely. Dedicated overlay objects are still hidden. Off by default.
Patch code-level censorship (Mono games, advanced) Deep opt-in: mosaic-named censor components (code, e.g. a MosaicController class) are stubbed in the game's managed DLLs — their Update/OnEnable/… method bodies are overwritten in place with an immediate return, so the censoring code never runs. Same-size edits, originals untouched, revert by re-exporting with the box off; but a bad patch could crash the game — test on a copy. IL2CPP games (no managed DLLs) are detected via their script metadata and reported as not patchable.

Fonts — why English overflows, and what the swap does

Why

Japanese Unity games usually render all text through a Japanese font, and Japanese fonts draw Latin letters wide (often full-width). Your English translations then overflow their UI boxes and wrap mid-word. Ticking Replace game fonts does two things. First it swaps the game's embedded legacy Font data for SLR Translator's own SLRCondensedCJK: its Latin glyphs are narrow, so English text fits the UI like it would in a Western font, and it still carries CJK coverage, so every string you did not translate keeps rendering in Japanese — no tofu boxes. Second — and this is what fixes TextMeshPro games — it re-renders the baked glyph atlases of the game's static TMP font assets from SLR's fonts: the JP font asset is re-baked from SLRCondensedCJK (so untranslated Japanese still renders), while every other TMP font asset (the default UI font) is re-baked from Stint Ultra Condensed — the narrow Latin face your translations were laid out for. The re-rendered atlases ship inside the patch as ordinary texture/font-asset files: the game draws its text in the new fonts without any runtime font re-rendering, so it works even on TMP builds that never rasterize fonts themselves.

Where

  • Strings projects: the Replace game fonts checkbox in the Export dialog (rows above).
  • Image projects: the same checkbox in the Insert translated images into a game copy tool (the swap then rides along with the inserted images in the game copy).

How it works

The swap rewrites the font data embedded inside the game's own font files (legacy Font objects and TextMeshPro font assets alike). Object names and references are preserved, so the game keeps using "its" fonts — they just contain SLRCondensedCJK instead. Nothing is added to the game and no game file is renamed.

The font-bearing files ride along inside the project (they are staged at creation like the string files), so a patch export can include them even when the original game folder has been moved or deleted. When the original folder is still where the project was created, it is consulted as well — so font files the project never staged (older projects, or a font file that failed to copy) are still found and swapped.

The TMP atlas re-bake keeps each font asset's geometry (point size, atlas size, padding, render mode) and regenerates its glyph/character tables and atlas pixels: the new character set is the asset's original characters ∪ ASCII ∪ every character used in your translations; glyphs the chosen font cannot provide are skipped and counted (the backend log carries the per-asset coverage). Layout metrics (line height, ascent, underline) are recomputed from the new font so vertical spacing stays consistent.

Limits

TextMeshPro with baked (static) glyph atlases is now covered by the atlas re-render (above): the frozen letter images are replaced with ones generated from SLR's fonts at export time. If text still renders wide on such a game, check the export summary line TMP font atlases re-rendered — a value of 0 with a skipped note means the re-bake declined those assets (e.g. the original atlas is too small for the character set at its point size), and those assets keep their original look; the backend log names each skipped asset and the reason.

Two smaller honest caveats: the default faces are fixed (SLRCondensedCJK for Japanese + Stint Ultra Condensed for Latin), though the export options carry two Custom font fields that accept your own .ttf/.otf for each role (dialogue vs UI) — a proportional font works but dialogue may overflow its boxes, a condensed face fits best; and if a resolved font file is missing from the SLR installation the export logs a warning and skips only the affected font stage (strings are still patched).

Demosaic — removing mosaic censorship

What it is

Many Japanese games ship their uncensored meshes and textures in the game data and add the mosaic censorship on top at runtime — a dedicated overlay object with a mosaic material, or a mosaic shader applied to the modeled mesh. The well-known BepInEx plugins (UniversalUnityDemosaics) hide those layers while the game runs, matching object names against a short list ("mosaic", "censor", "pixelate", …) every single frame. SLRUnity's demosaic does the same job statically and in place: at export it finds those layers in the game's serialized data files and writes a patched copy — no BepInEx, no runtime hooks, nothing installed into the game. Your original game folder is never modified; export again with the checkbox unchecked (or delete the two patched files) to revert. The same treatment is available without any project as the New Project slide's Remove mosaic censorship (standalone) tool — for games that are already translated.

What gets patched

  • Mosaic-named objects (e.g. a GameObject called mosaic) are hidden: the object is deactivated and its renderers stripped, so nothing renders even when the game's own scripts turn the object back on mid-scene.
  • Mosaic materials are neutralized: the material is re-pointed to the game's own transparent/unlit shader, its texture slots are cleared and its colors set to fully transparent — a static version of what the runtime plugins do to combined meshes. Renderers whose every material is a mosaic candidate are hidden outright (mixed combined meshes are never hidden — only their mosaic material is neutralized).
  • Detection evidence goes beyond names: a shader whose serialized property table names mosaic parameters (_PixelSize, _MosaicStrength, …) counts even when the shader's name was stripped from the build (which happens).

The export summary reports what was found — per-action lines like hidden object 'mosaic' (object name 'mosaic') — and says so explicitly when the stage ran but found nothing. The detection level option trades precision for coverage: high (default) only patches unambiguous candidates; medium also patches weak-only evidence such as a shader carrying only the typical _sizeMin/_sizeMax block-size pair.

The two advanced tiers cover the remaining UniversalUnityDemosaics techniques. Reveal instead of hide is the automatic version of UUD's ShaderReplace/MaterialReplace: mosaic materials on modeled meshes get the game's own display shader with their textures kept (the display shader is found automatically — the game's most-used skin shader, the thing UUD makes you look up by hand with RuntimeUnityEditor). Patch code-level censorship is the static DumbTypeDemosaic: censor component classes found by name in Assembly-CSharp.dll get their Unity lifecycle methods stubbed to immediate returns — same-size in-place edits that leave the component, its fields and every other method intact, so callers keep working and the game boots normally. The scan always reports censor-suspect script classes (Mono and IL2CPP both carry the class names in their data) even with the tier off; on IL2CPP games the tier explains that native-compiled code cannot be patched statically — the same gap UUD has (it ships no IL2CPP variant of that plugin either).

Honest limits

  • Mosaics created purely in code (materials built at runtime with no serialized counterpart) are invisible to a static scan — the stage honestly reports "no candidates" on such games rather than guessing.
  • Material rendering is not visually verifiable by the tool: the material neutralization picks the game's own shader by pipeline (URP vs built-in) and sets transparent-surface parameters, but only you can confirm the scene actually looks right — check an H scene after exporting.
  • A game that resets a material's shader from code at runtime (rare) can undo the material patch; the object/renderer hiding still applies. Code-level censorship (a censoring Behaviour rather than assets) is covered for Mono games by the opt-in code tier (lifecycle methods stubbed in the managed DLLs — a malformed patch could crash the game, so test on a copy). On IL2CPP games the code is native machine code and cannot be patched statically; the scan still reports the suspect classes. Censorship inlined into unrelated game code (no dedicated class) is not name-detectable — that holds for UUD's plugin too.
  • Projects created before this feature keep working: the export warns that such a project's staging predates mosaic scanning — re-create the project (or use the full game copy export kind, which scans the original game) for full staged coverage.

Understanding the project file list

Unity games store text in several different places. The project's file tabs are the game's real storage — here is what each kind means:

  • level0, level1, … levelN — Unity scenes, not game "levels". The number is the build index: the order scenes appear in the game's build settings (level0 is usually the title/boot scene). Everything that exists in a scene — including UI canvases — is serialized into it. Many games keep their whole menu/UI in every scene, so level1…levelN can look almost identical: same Achievement list, same settings labels, same dialogs. That is the game's doing, not a scan error.
  • You do not need to translate the duplicates. Translation is keyed by the original text: fill in the string once (in any one of the copies) and export writes that translation to every occurrence in every file. Blank duplicates are simply skipped.
  • global-metadata.dat — text baked into the game's compiled code (IL2CPP string literals; contexts look like literal #18492). These are patched by rebuilding the metadata blob — any translation length.
  • localization-string-tables-japanese(ja)….bundle — Unity Localization string tables: usually the bulk of actual dialogue. chinese(simplified) is the game's own Simplified Chinese table (often a near-copy of the Japanese — leave blank to skip it), and english(en) is any English the developers already shipped.
  • sharedassets*.assets / resources.assets — shared objects, including TextAssets (credits, readmes — contexts like お借りしたもの L0 = line 0 of that asset).
  • …_monoscripts….bundle — script metadata; normally contains no translatable text.
  • Games with custom font glyphs — eroge often re-purpose rare characters (box-drawing arrows and the like) as moan/emphasis marks in custom fonts. The scan treats those glyph characters as ordinary text, so bubble quips like あっ┻…んっ┻ are collected and translated like any other line.

The context column tells you where a row lives: Canvas/NewGameCheck/confirm/Text (TMP) is the GameObject hierarchy path in its scene (also what the scene graph sends to the LLM as scene context); literal #N is a code literal; $.a.b[0] / r1c1 / L2 are JSON-path, CSV-cell and line-number keys inside TextAssets and text files.

Limitations

  • Mono games' Managed DLLs: Japanese literals compiled into managed code (Assembly-CSharp.dll … — intro cinematics, one-off lines) are translated since v2.6: the export rebuilds the DLL's string heap compacted — the space the Japanese text occupied is reclaimed for the English, every reference is repointed, and the result is verified against the game's own Mono runtime. There is no fixed size limit: the DLL grows to hold the English (verified against the game's own Mono runtime), so complete coverage is the norm. Rows appear on re-creating the project.
  • IL2CPP games: literals in compiled code are translated, via a rebuild of global-metadata.dat.
  • TextAsset JSON formatting may change (indentation/key order) when a JSON TextAsset is patched; the content stays equivalent.
  • Scene/object strings are rewritten in place; if the game rebuilds or re-serializes its own data at runtime, patched text persists but heavily obfuscated or custom-compressed assets are out of scope.
  • No font is bundled: the font stages use SLR Translator's own fonts — SLRCondensedCJK (www/core/SEP/SLRCondensedCJK-Regular.ttf) for the swap and the Japanese atlas re-render, Stint Ultra Condensed (fonts/sucr.ttf) for the Latin/UI atlas re-render. If a file is missing, the export logs a warning line in the overlay console and simply skips the font stage (strings are still patched).
  • Static TextMeshPro atlases are re-rendered by Replace game fonts: baked glyph atlases are regenerated from SLR's fonts at export time (Latin/UI from Stint Ultra Condensed, Japanese from SLRCondensedCJK), so narrow English applies even to TMP games — no runtime font rendering involved. Assets whose atlas is too small for the requested character set are skipped with a logged reason (original look kept). See Fonts.
  • Demosaic (mosaic censorship removal) is heuristic by nature: it matches names and shader-property evidence in the serialized assets, so it will not fit every game — mosaics drawn purely from code, or censorship implemented as game logic rather than assets, are reported as "not found" instead of guessed at. See Demosaic.

Troubleshooting

SymptomWhat to do
The Unity engine does not appear in New Project at all The addon folder is wrong or the bundled runtime is missing. Verify www/addons/SLRUnity/package.json exists and that runtime/python/python.exe (Windows) or runtime/bin/python3 (Linux) is present inside the same addon folder, then restart. Without its runtime payload the addon stays completely silent by design (no SLRUnity entry in the New Project dialog is the visible symptom).
"No Unity game found" / "Multiple Unity games found" alert The picked folder is not a Unity game root (no UnityPlayer.dll/GameAssembly.dll, no <Game>_Data with Unity data files) — or it contains SEVERAL Unity games, in which case pick the specific game folder directly.
"Unity scan failed" / "Unity patch failed" alert The alert names the exact backend.log path — by default <SLR>/www/php/cache/<project id>/jobs/backend.log. The last entries contain the full Python error and traceback.
Error mentions "unsupported contract version" The JS addon and the Python backend come from different builds. Delete www/addons/SLRUnity/ and install the complete current package again (extract the archive over a fresh folder) so both halves match.
"Full copy export needs the original game folder (...)" You picked full game copy but the original game folder the project was created from no longer exists (moved/deleted/other machine). Nothing was exported. Switch the Export kind back to patch — the project carries its own copy of every string-bearing file, so patch export works without the original. If you truly need a full copy, point a folder with the same game back at the same path first.
Export logs WARNING: "N staged edits did not land" in the overlay console Some strings could not be rewritten in place (details in backend.log). The game still runs; check whether the affected strings display translated. Report the game if it recurs.
"Nothing to export in full game copy mode" Only full game copy can have nothing to do: with every translation still blank and the font swap off, a full copy of the unchanged game would be a no-op. Fill in translations, tick Replace game fonts, or switch the Export kind back to patch — patch export always works: it writes translated files plus verbatim originals (revert) for everything else in scope, so even a no-change export produces a valid all-originals patch. Image translation does not go through this dialog: it is a separate flow (New Project → SLRUnity → Extract/Insert textures).
"No unity_img_manifest.json found" (Insert translated images) The folder picked as "extracted-images folder" is not the one the Extract textures tool created — that tool writes unity_img_manifest.json next to the PNGs, and Insert needs it to map images back into the game files. Pick the <Game>_unity_img folder (or wherever you kept the pruned copy of it).
The patch export's output folder doesn't contain the whole game That is by design: the default patch export contains the changed files plus the originals of every other file in scope (all project files unless you checked a subset in the file list), at their game-relative paths. Copy those files over your game folder to apply. If you want a complete runnable copy instead, choose full game copy as the Export kind (needs the original game folder).
Checked Replace game fonts, exported, applied — but the text still renders wide Check the export summary: if TMP font atlases re-rendered is missing or 0, the atlas bake did not run or declined the assets (a missing font file — see the WARNING lines in the overlay log — or an atlas too small for the character set; the backend log names each skipped asset). If it is > 0, re-apply the newest patch to the game folder — the re-rendered atlases are ordinary game files and an older patch will not update them. See Fonts.
Zip export fails with a 7-Zip exit code The alert includes 7z's stderr and the staging folder path — the exported files are still there and can be zipped manually.
